Security

It decides what runs. So it is built like it.

An application control platform is as sensitive as a domain controller: whoever controls it decides what every machine may run. This page explains how ENFORZ protects its keys, its sign-in, its agents, its record and the appliance it runs on.

Keys

Every key has one job

Each key below does one thing, and none of them can stand in for another. The policy-signing key and the payload-signing key are kept apart by design, and neither leaves the appliance in usable form.

KeyWhat it doesHow it is kept
Payload-signing keySigns every assignment and policy the appliance sends. One per platform.Its public half is compiled into the agent. The agent never accepts a key from configuration, the installer or the TLS connection, so a hijacked server or a rewritten config file cannot impersonate the appliance.
Agent client certificatesIdentify each machine to the appliance, issued by a per-organisation CA at enrolment.Valid for 24 hours and renewed automatically. The organisation comes from the certificate, never from anything the machine writes in a message or a header.
Agent code-signingAuthenticode signature on the agent binary.Every policy must contain a rule matching this signer or it is not sent. When the signer rotates, the new signer reaches every machine's policy, confirmed by heartbeat, before an agent signed with it ships.
Policy-signing key (firmware protection)CI-signs enforced policies for the EFI partition. Optional.Its own key, never the payload key. Sealed under a password a person types each time it is used, with an escrow copy kept offline. Unused until a signing test has been recorded as loaded.
Release keysSign appliance update bundles.The appliance verifies a bundle before changing anything. A second rotation key is kept offline, so a lost signing key can be replaced without trusting anything new.
BitLocker sealing keySeals each machine's recovery key before it leaves the machine.RSA-4096, its public half built into the agent. The private half is wrapped with scrypt and AES-GCM under a passphrase that is never stored. Opening one is throttled and recorded.

Sign-in

Passkeys, SSO and a way in when SSO is down

Passkeys first

Every local account proves a second factor before any page loads. Passkeys are preferred because they cannot be phished, authenticator codes are the fallback, and an administrator can require passkeys only.

Codes that cannot be replayed

The authenticator secret is sealed at rest. A code that was just used is refused, and the QR code is drawn on the appliance, never by an outside service.

Single sign-on with OIDC

Entra ID, Okta, Google Workspace, Keycloak or AD FS through OpenID Connect. The identity provider says who someone is; what they may do is set in ENFORZ, and a new person has no access until an administrator grants it.

A way in when SSO is down

Local accounts keep working when the identity provider does not, so an outage at the provider cannot lock you out of the system that decides what runs.

Lockouts and roles

Ten failed sign-ins lock an account for 15 minutes. Four roles, from Viewer to TenantAdmin, per organisation. Every sign-in and role change is in the audit log.

Recovery that needs the appliance

A lost second factor is reset by another administrator, or from the appliance itself. There is no email link to intercept.

Agents

Every machine talks to one server. That server is not a way in.

The front door takes writes only

The service agents talk to can put messages on a queue and do nothing else. It cannot read the database, make decisions or generate a policy, so its hostile-input boundary is small enough to read in full.

Assignments from pre-written files

Machines fetch their assignments from signed files written ahead of time, not from queries against the database. A flood of requests reaches no business logic.

Unreachable pauses telemetry, never enforcement

If the appliance goes offline, agents keep their policy and spool their events. No code path relaxes enforcement because the appliance cannot be reached, so taking it down cannot switch protection off.

It cannot lock itself out

A policy that does not trust the agent's own signer is never sent. Uninstalling takes our policies off first, and is refused while one of ours is enforcing.

Counts are evidence, not decisions

Telemetry is never thinned out to save bandwidth at the cost of counts, because the signals that catch a masquerading binary are built from it.

No rule without a person

No path creates an allow rule without a signed-in, audited human: not for trusted publishers, not from reputation services, not from the AI assistant, not for a pilot.

Logs and SIEM

Everything on the record, and a copy where you keep yours

An audit log nothing can edit

Every approval, revocation, build, promotion, waiver, break-glass, sign-in and settings change, with who did it and the reason they gave. Rows cannot be modified or deleted from the product.

Shipped to your SIEM

The audit log, and alerts if you choose, as CEF, LEEF 1.0 or JSON inside RFC 5424 syslog. TLS (RFC 5425) is the default; TCP and UDP are there for collectors that need them. Each event type maps to a severity.

AI with a receipt

The assistant is off until you turn it on, under your own account. Evidence is anonymised before it leaves, and every request is recorded and readable in full.

Support bundles redacted at source

Logs are collected and redacted on the appliance before anyone downloads them.

Appliance hardening

Hardened before it reaches you

The appliance ships as a hardened Debian virtual machine. None of this is a checklist for you to work through after import.

SSH is closed by default

The appliance ships with SSH firewalled off and no key installed. It opens from the console menu with a public key you paste, and the menu offers to close it again when you log out.

Keys only, no root

PermitRootLogin no, password and keyboard-interactive login off, three attempts, a 30-second grace period, no X11, agent or TCP forwarding. The root account is locked.

fail2ban

Four SSH failures in ten minutes ban the address for an hour. Bans and failures can be viewed and cleared from the console menu.

A firewall that denies by default

Incoming traffic is refused except the web console (HTTP redirects to HTTPS) and the two agent ports: mutual TLS for telemetry, and server TLS for enrolment.

A kernel with fewer secrets

Restricted kernel logs and pointers, full address-space randomisation, ptrace limited to parent processes, and unprivileged BPF disabled.

Patched without asking

Debian security updates install automatically every day. The console shows when a new kernel needs a restart, and the restart can be scheduled.

TLS 1.2 and 1.3 only

The web console sits behind nginx with modern TLS and per-client rate limits. Cloud-init is disabled once first boot is done.

Signed updates with a way back

ENFORZ updates are verified against the release key before anything changes, and the previous version can be restored in one step.

Console lockdown

Backup, restore, the root shell and SSH can each be locked from the console menu, so a stolen console login cannot reach them.

A console that cannot approve

The text console manages the appliance. It has no way to approve software, build a policy or enforce one. Those stay in the web console, behind sign-in, roles and the gates.

Recovery

Every path to enforcement has a way back

The recovery menu stays

Advanced Boot Options Menu is in every policy template and cannot be switched off, so a machine can always reach Windows recovery.

Break-glass

One machine back to audit for a limited time, from the console, from your deployment tool, or from the emergency store if the appliance itself is down.

Rehearsed before it is real

Simulation, shadow audit, soak and a Canary ring, so enforcement reaches each machine only after it has been rehearsed against real telemetry.

Firmware protection removed only by the signed sequence

A CI-signed policy in EFI is never deleted, unloaded or replaced unsigned. It comes off through a signed removal sequence of two restarts, and an unsigned policy is never placed in EFI.

Trust

It decides what is allowed to run

That makes it one of the most sensitive systems you will own, and it is built on that assumption.

The front door takes writes only

The component the agents talk to can put messages on a queue and nothing else. It cannot read the database, make decisions or generate a policy.

Machines identify themselves with a client certificate rather than anything they can claim in a message or a header. The hostile-input boundary is deliberately small enough to read in full.
One key, compiled in

Agents verify instructions against a key built into the binary, not one supplied by the server, the installer or the connection.

Everything attributable

Every approval, promotion, waiver and break-glass window is recorded against a person, with what was waived and why.

Your data stays yours

Telemetry, inventory and policy live on your own server. Nothing is shared with us or transmitted to us.

The optional AI assistant is the one exception, and only when you turn it on. It sends anonymised evidence to the AI provider you choose, under your own account, and records exactly what each request contained.

It arrives as an appliance

The platform ships as one virtual machine for Hyper-V (VHDX) or VMware (OVA), and cloud images are available too. The operating system underneath is hardened and patched as part of the release, so there is no build for anyone on your side to get right.

  • 1Import the image. One file into Hyper-V or VMware, or start the cloud image. It boots configured.
  • 2Enrol a pilot ring. A handful of machines you can reimage, in audit mode, blocking nothing.
  • 3Work the queue, then rehearse. Approve, simulate, soak, and promote one ring at a time.
MCP server

MCP, with the same boundaries

The Model Context Protocol server lets your own AI tools read the console. It follows the rules above: off by default, per-person tokens scoped to one organisation and read access, every call in the audit log, and no path to approve, build or enforce.

ENFORZ builds, reviews and deploys Windows application control policy from what your own machines really run. Telemetry, an approval queue no rule escapes, simulation against real events, and enforcement behind fourteen gates that fail closed. On one server you own, with nothing reported back to us.
