On every machine

The agent

One signed service that reports what runs and applies what you decided. It never decides anything itself.

Telemetry

  • One small Windows service. Written in C# on .NET 10, shipped as a single self-contained file, Authenticode-signed, running as SYSTEM. No PowerShell scripts doing the real work, no runtime to install.
  • Signer-aware telemetry. Reads App Control's block and audit events and joins each one to its separate signer event by ActivityID, so a signed file is never mistaken for an unsigned one and pinned by hash.
  • Catalog-signed files. Files signed through a Windows catalog rather than in the file itself are looked up, so they are attributed to their real publisher.
  • Counts are never dropped. Repeated events are folded into 15-minute rollups that carry every count and the new paths seen. Only duplicate detail is skipped, never how often something happened.
  • Works offline. If the appliance cannot be reached, events go to a local spool and the applied policy stays exactly as it is. On reconnection the spool drains on a stagger, and anything lost is reported as a gap.
  • Event storms handled. A flood of events is shed into a bounded, sampled read. Signer and policy-lifecycle events are always kept.

Applying policy

  • Policies applied without a restart. Uses CiTool to load and refresh policies live, including the single-format policies Windows Server 2019 needs, and reports the version Windows actually loaded.
  • Knows who owns each policy. Every policy on the machine is classified from evidence: ENFORZ's, Windows' own, Intune's, Group Policy's or another tool's. That way a removal is never undone at the next sync.
  • Checks every instruction. Every assignment is verified against the platform's public key compiled into the binary. A key from configuration, the installer or the TLS connection is never accepted.
  • Its own identity. A per-organisation client certificate valid for 24 hours, renewed automatically. The machine's firmware UUID tells a reinstall apart from a different machine reusing the name.
  • Managed installer. Applies the AppLocker managed-installer rule, so software your deployment tool installs is trusted by origin.
  • Removal code. Uninstalling asks for a per-machine code once one is set. Uninstalling also takes ENFORZ's policies off first, and is refused while an enforced policy of ours is active.
  • Self-diagnosing. A watchdog that records where the service was when it stopped responding, and a memory ceiling it watches itself.

What it can report

  • Inventory, opt-in. Installed programs, the Windows build, loaded drivers with their hashes, and BIOS details. Sent only when something changes, and deleted when collection is switched off.
  • Program usage, opt-in. Which approved software is still started (Security event 4688 and a process list), so stale approvals can be retired.
  • Signed-in users. Who is on each machine now, so the fleet can be searched by person.
  • Security tools watch, opt-in. Whether antivirus, EDR and your own listed services and processes are running, with their versions.
  • BitLocker. Each volume's protection state and recovery key IDs. Each recovery key is sealed to your public key before it leaves the machine.
  • Block notice. Explains a block to the person at the machine: a corner pop-up, a Windows notification or both, in your words.
Review

From events to decisions

The queue, the evidence beside it and the assistant that drafts. A person makes every decision.

Approvals: the review queue

  • Decisions, not events. Tens of thousands of block events are collapsed into one row per application: grouped by signer, product, folder and file name, with the machines, users and paths behind each.
  • Six rule levels. Issuing CA, Publisher, WHQL publisher, FilePublisher, SignedVersion and Hash, each explained in plain words beside the Approve button, with a warning when a level trusts more than the evidence supports.
  • Risk signals. A file masquerading as a Windows name, unsigned code in a folder users can write to, a downloaded binary, a driver Windows refused, and reputation hits. Anything above Low has to be expanded and its warnings acknowledged.
  • PCs and servers apart. Servers follow their own base policy. The queue, approvals and rings keep the two lines separate.
  • Bulk review. Review several groups side by side and decide them together. One explicit acknowledgement must still cover everything selected.
  • Companion files. The helper DLLs and executables that travel with an approved application, approved as one decision that still lists every file.
  • History and pending changes. Every approval and withdrawal, with which policy carries it and whether that policy is on machines yet. An approval no machine has received yet can be undone.
  • Hidden items. Things put out of sight, with the standing rules that hide them. Hiding never approves anything.

AI assistant (off until you turn it on)

  • Draft plan. Claude groups the undecided queue and proposes allow, keep blocked or needs a human for each group, with its reasoning and concerns. You approve groups in one step, as yourself, through every normal check.
  • Guided review. One group per screen: the facts, what the AI says, what each rule level would allow, and your decision.
  • Policy review. A second reader for any build: over-broad trust, approvals whose risk changed, kernel grants, duplicates and recovery options.
  • What was sent. Every request is recorded with its fingerprint and size, and can be read in full. Evidence is anonymised before it leaves the appliance.
  • Your account, your limits. Claude through the Anthropic API or Microsoft Foundry under your own key. Daily request limit, monthly budget and the cost of each run are shown. It never approves anything.

Detection and evidence

  • Inspect a file. Upload an installer and read its real signer before any machine is blocked by it. The result lands in the queue as a normal row.
  • Suspicious blocks. Scored triage, separate from the approval queue: Critical, High and Elevated items with the signals that raised them.
  • Remote access tools. Remote monitoring and remote desktop tools flagged from the community LOLRMM catalogue, except the ones you say you use.
  • Hash reputation. VirusTotal, MetaDefender, MalwareBazaar and CIRCL hashlookup, with your own keys. Advisory only: reputation never makes a decision.
  • Vulnerabilities. Installed software, drivers, BIOS and Windows builds matched against Microsoft's security updates and vulnerable driver list, the CVE List and NVD, CISA's exploited list and FIRST EPSS. Coverage tells you what could not be assessed.
  • Endpoint protection. Each machine's security tools: running, stopped or missing.

Keeping approvals honest

  • Recertification. Approvals expire and come back for a decision, so software that has left the estate does not stay trusted forever.
  • Policy hygiene. Approvals that another approval already covers, revoked one at a time with a reason.
  • Application requests. People ask for blocked software in their own words and follow the answer. A request allows nothing on its own.
  • Notifications. Email, browser push and Microsoft Teams, sent straight away or in a digest. You can also build your own alerts and preview them against last week's events.
Policy

From decisions to enforcement

Builds you can read, a rehearsal against real telemetry, and enforcement one ring at a time, with a way back.

Building policy

  • Base policy and options. Start from Microsoft's recommended base or your own. Rule options are switches, and the ones that must not change are locked. Advanced Boot Options Menu, the recovery path, is in every template.
  • Base policy rules. See what an imported base contributes, signer by signer and deny rule by deny rule, and choose which of it to keep.
  • Microsoft's block lists. The recommended block rules and the vulnerable driver blocklist, versioned and adopted deliberately. A list that is malformed, unexpectedly short or contains allow rules is refused.
  • Application groups. Software for a specific audience (Finance, Engineering) as supplemental policies, so one strict base serves everyone.
  • Releases. Every build is a numbered release with a diff against the last one, the approvals behind every rule, and where it runs now.
  • Policy explorer. What a policy allows, each rule traced to the person who approved it, and a check of whether a specific file would run.
  • Effective policy per machine. The base plus every supplemental that applies to one machine, in one view.
  • Self-lockout check. No policy is sent unless it contains a rule matching the agent's own signer. A failed check stops the policy.
  • Compiler. A Windows worker compiles each build with Microsoft's own cmdlet. The compiled file is read back and checked against what was intended before it is accepted.

Getting to enforcement safely

  • Rings. Canary, Pilot, Broad, Full and an Audit ring for new machines. Each ring carries one assignment, and machines move between rings deliberately.
  • Simulation. Replays real telemetry against a draft and lists every file it would block and every machine affected, before anyone is affected.
  • Shadow audit. Run the next build in audit alongside the build a ring already enforces, and compare what it would block.
  • Soak and gates. Fourteen checks before enforcement: observation time, simulation, decided findings, soak, a typed count of affected machines, a second approver, a signed agent and more. All of them fail closed.
  • Enforce one machine first. Set up a single machine as the first to enforce, without skipping a single gate.
  • Rapid push. Send an urgent supplemental, or tell machines to fetch their own assignment now, through your deployment tool.
  • Break-glass. Move one machine back to audit for a limited time, through the console or your deployment tool. The window expires on its own and is recorded.
  • Firmware protection. Opt-in for an enforcement build: CI-signed copies kept in the EFI partition, so a local administrator cannot remove them. Requires the build, the machine, a recorded signing test and a typed password. Removed only by the signed removal sequence.
  • Handover. Export everything to another platform, or import another platform's decisions and apply them one ticked row at a time.
Fleet

Every machine, and how the agent gets there

Machines

  • Fleet. Every machine: user, agent version, ring, policies, App Control state, Secure Boot, firmware protection and health, with search by name or person.
  • Coverage. Domain computers with no agent, and agents with no directory object, read from Entra ID through Microsoft Graph or from on-premises AD over LDAPS.
  • Policies from elsewhere. Every policy ENFORZ did not deploy, classified once per GUID across the fleet, with a request to remove it from the machines you choose.
  • Drift. A machine running a policy nobody deployed, or not running the one it was given.
  • Same machine. When a reinstalled machine enrols again, an administrator can hand the old record's name, rings and groups to the new enrolment.
  • BitLocker. State, recovery key IDs, AD and Entra escrow checked by key ID with metadata-only rights, and sealed copies opened with a passphrase that is never stored.

Getting the agent there

  • Enrolment. Single-use, time-limited tokens. The token is shown once, and only its hash is kept.
  • Push agent. Build the installer and hand it to your deployment tool for the machines you confirm on a separate screen.
  • PDQ Connect, Intune, Action1 or manual. One deployment tool per organisation installs and updates the agent, pushes urgent policy and carries break-glass. Scripts handle machines already in Constrained Language Mode.
  • Emergency delivery. Each machine's current assignment, signed and placed in a cloud store you own, so machines can fetch it while the appliance is down.
  • Removal. A removal package and per-machine removal codes. Un-enrolling is refused while a machine still enforces a policy of ours.
Record

What happened, and who did it

The record

  • Raw events. The unaggregated telemetry behind every queue row, read-only, with a button that only ever creates a row to decide.
  • Audit log. Every approval, revocation, build, promotion, waiver, sign-in and settings change, with who did it and why. Append-only: nothing in the product can edit or delete a row.
  • Alert history. Every alert raised in the last 90 days, what it said, and how and to whom it was sent.
  • SIEM connector. The audit log, and alerts if chosen, sent as CEF, LEEF or JSON in RFC 5424 syslog over TLS, TCP or UDP.
System

Access and the appliance

How people sign in, and how the appliance looks after itself. Security goes deeper.

Access

  • Single sign-on. OpenID Connect with Entra ID (with a setup script that creates the registration), Okta, Google Workspace, Keycloak or AD FS. A new person who signs in has no access until an administrator grants it.
  • Passkeys and authenticator codes. A second factor for every local account, enforced before anything else. An administrator can require passkeys only.
  • Roles. Viewer, Approver, PolicyAdmin and TenantAdmin, per organisation. Every change of role is in the audit log.
  • Organisations. Several organisations on one appliance, each with its own data, keys for its agents, rings and people.
  • Sign-in lockouts. Ten failed web sign-ins lock an account for 15 minutes. Lockouts can be cleared from the console menu.

The appliance

  • Ships as a virtual machine. Hyper-V (VHDX), VMware (OVA) or a cloud image, hardened and configured on first boot.
  • First-run checklist and guided rollout. What is set up, what is missing, and the next step, from enrolment to enforcement.
  • HTTPS certificate. Replace the self-signed certificate from the console. Agents and browsers then trust the appliance.
  • Encrypted backups and restore. Passphrase-encrypted backups of everything, kept on the appliance or copied off, restorable from the web console or the console menu.
  • Signed updates. Update bundles are verified against the release key before anything changes, with a one-step way back to the previous version.
  • OS security patches. Debian security updates install automatically, with a restart when a new kernel needs one, scheduled from the web console.
  • Support bundles. Logs collected and redacted on the appliance before you download them.
  • Appliance console. A text menu at the VM console or over SSH: network, certificate, backup, restore, building the agent, services, logs, SSH access, lockdown, updates and reboot. It cannot approve software or enforce policy.
  • MCP server. Read access to the console for your own AI tools through the Model Context Protocol, scoped per person and organisation, audited, and off by default. Drafts only: approving stays in the console.
  • No phone home. No licence check, no activation and no usage telemetry. Nothing is sent to us.
The bypass that defeats most allowlists

Windows ships the attacker's tools already signed

Certutil downloads files. Mshta runs script. Regsvr32, rundll32, msbuild and the debuggers all execute code on someone else's behalf. They are legitimate, Microsoft-signed and already on every machine, so a list built purely from what your fleet runs will allow every one of them, and an attacker who has any of them does not need to bring a binary at all.

The deny list is part of every build

Microsoft maintains the list of its own signed binaries that can be used to get around application control. The platform keeps a current copy and merges it into every policy it compiles, so the hole is closed by default rather than by remembering.

Several hundred deny rules. The copy is fetched and offered as a version; an administrator adopts it and that is recorded. Deny rules only: a list that does not parse, comes back unexpectedly short, or contains anything other than denials is refused outright instead of half applied.
An imported policy is usually stale here

Most published base policies carry a copy of this list frozen at whatever was current when the base was written. Anything Microsoft has added since is simply missing, and nothing tells you.

Because these are denials, adding newer ones tightens an enforced policy. That is treated as a tightening: named at the enforce step, simulated, and accepted by a person rather than slipped in.
And it argues with you about the rest

When a decision in your queue involves one of these binaries, the review says so and says why: allowing it can effectively allow anything it goes on to launch. The same applies to a system filename found outside System32, or a program started by Word or Outlook.

These are reasons to look twice, not automatic denials. The point is that the risky ones stop looking identical to the other four hundred items in the queue.
Why it matters

An allowlist that allows mshta.exe allows everything mshta.exe can be told to run. Allowlisting without this is a lock on a door with the window open, and it is the single most common way an application control rollout turns out to be worth less than it looked.The vulnerable-driver blocklist is handled the same way, for the same reason: a signed driver with a known flaw is how security software gets switched off.

On every machine

One small service, and no open door

A single signed Windows service does the work on the endpoint: it watches what runs, applies the policy that machine was assigned, and holds the break-glass key. It carries its own runtime, so there is nothing to install underneath it.

It collects, and it tidies up first

Every launch on the machine is an event, and the signer is recorded in a separate one. The agent matches the two together locally and collapses the repeats, so what reaches the console is readable instead of a transcript.

Correlating on the endpoint is why forty thousand raw lines arrive as a couple of dozen decisions. The counts are preserved: collapsing never hides how often something ran.
It only ever dials out

The agent opens no port and accepts no connection. It reaches out on its own schedule, identifies itself with a certificate it enrolled and renews by itself, and asks whether anything has changed.

There is no inbound management channel to find, authenticate against or abuse. A machine is known by the certificate it holds, not by a name it puts in a message.
It applies what it was assigned

Policies are fetched, checked against a key compiled into the agent itself, and applied. A policy that does not verify is not applied, whatever told it to.

It holds the break glass

When somebody has to be let past, the agent takes a signed instruction addressed to that one machine, with an expiry on it, switches that machine to the audit copy of its policy, and puts it back when the window closes.

A statement issued for a different machine is refused. So is an old one replayed later. The window is in the audit record with who opened it, on what, and for how long.
It survives the outage, and admits the gap

Events are spooled to disk and survive a reboot or a server that is down. If the spool fills and the oldest have to go, it says so on the next check-in.

A declared gap matters because simulation is only as honest as the telemetry behind it. Silently losing events would make a policy look safer than it is.
Losing the server changes nothing

If the console is unreachable, telemetry pauses and enforcement carries on exactly as it was. The agent never relaxes a policy to get itself out of trouble.

It has a watchdog, and the watchdog only reports: it names the step the agent stopped in, and never restarts, reverts or loosens anything on its own authority.
While it is watching anyway

An inventory nobody had to collect

To decide what may run, it already knows every binary, driver and version in the estate. That answers questions no separate tool had to be bought for.

What is out of date, and dangerous

Known vulnerabilities matched against what is genuinely installed and running, per machine, rather than against a list of product names.

Three kinds of finding. Windows builds measured against the update that fixes a given issue. Loaded drivers matched against known-vulnerable driver lists. Third-party software matched by version against a curated catalogue with deliberately conservative ranges, and each finding says how it was reached.
The driver nobody knew was there

Vulnerable drivers are how attackers switch off your security software. They are also invisible to most inventories, because nothing ever asked.

A second opinion on a hash

Look up anything you are unsure about and see an outside reputation verdict next to your own evidence before you approve it.

What is still uncovered

Which machines have the agent, which are enrolled, which are enforced, which are only in audit, and which are not covered at all.

Push without a separate project

Where you already use a deployment tool to put software on machines, it can hand the agent over to it rather than making you build a rollout.

A deliberately small integration with PDQ Connect: list the devices in a group, create a deployment, nothing more. The credential can reach the whole fleet, so the surface is kept to what the feature needs.
Blocks worth looking at

Not every block matters. The ones that do, where something unsigned ran from a folder a user can write to, are separated from the noise.
